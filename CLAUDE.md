# CLAUDE.md

Guidance for Claude Code in this repository: structure, principles and traps. Users read `README.md`; reference material (building, troubleshooting, scripts, the conformance suites) is indexed in `docs/README.md`. Do not put numbers that a tool measures (coverage, case counts) here - they go stale; point at the tool.

## What this is

Hodow is a hobby CLI tool with a web dashboard that validates specific CPU (x86_64/ARM SIMD) and GPU (OpenGL, Vulkan compute) instructions/functions by actually running them and checking results, to catch hardware/driver bugs rather than software bugs. It must stay cross-compilable without native (C/C++) dependencies. It relies heavily on AI-assisted code generation (README.md "AI usage").

**Target platforms:** desktop and embedded devices running Linux (Yocto, ordinary distros, any architecture: x86, ARM, RISC-V, ...) or Windows; macOS only for the CPU tests, burn, bench and the dashboard (no GL, no CTS: no EGL, and glutin's CGL has no pbuffers). Nothing else is a target, so port no platform-specific code or variants for anything outside that list.

**Never open `/dev/mem`, `/dev/kmem`, `/dev/galcore` or map device registers** from any code, script or test: it causes problems on Vivante boards. Kernel and GPU state comes from /proc, /sys and the kernel log only (a `stat` of `/dev/galcore` to detect the driver is fine).

## Lints and warnings

`Cargo.toml` holds the lint set of the rust-setup skill for the hand-written crates (`hodow`, `hodow_common`, `hodow_cpu`, `hodow_gpu`, `hodow_bench`), with four lints switched off for stated reasons (`indexing_slicing`, `undocumented_unsafe_blocks`, `print_stdout`, `print_stderr`). The `hodow_cts` crates have their own short table (ported C++ keeps its shape); generated code is exempted at the module that declares it, never by editing it. A justified exception is `#[expect(lint, reason = "...")]` at the narrowest place that accepts an attribute (a `let`, a match arm, an item; an assignment or `if` statement cannot carry one, so the enclosing `fn` does). When whether a lint fires depends on the feature set, `expect` goes unfulfilled in some builds: use `#[allow(clippy::allow_attributes, lint, reason = "...")]` or a `cfg_attr`. New warnings are fixed, not allowed; check every feature set CI builds, and the cross targets (`cargo check --target x86_64-pc-windows-gnu` and `aarch64-unknown-linux-gnu` for the Vulkan half: `std::os::fd`, `c_char` being `u8` on ARM and `libc` calls that exist only on Linux are what broke before).

## Committing - do it yourself, without being asked

Commit finished work on your own initiative, straight to `master`; the usual "ask first" rule is waived here. **Pushing is still not yours to do** unless asked.

A commit is a unit that is *finished and checked*, not one that merely compiles:

- The checks that apply have been run and pass. For a `hodow_cts` group that means its whole acceptance gate: `just cts-diff` / `cts-gles-diff` (`diff_vs_deqp.py`) agreeing with upstream decides - a group that has not been diffed is not finished.
- `just clippy` (hand-written crates) and `just cts-clippy` report no warnings, and `just fmt-check` is clean. The compiler's own warnings count the same: `cargo check` of the feature sets that CI builds is warning-free.
- A change to the dashboard page passes `just serve-ui-test`; one to `hodow_common` passes `cargo test -p hodow_common`.
- Generated files were regenerated by their generator, never hand-edited, and re-running the generator is diff-clean.

Do **not** commit work in progress, a tree that fails its own gate, or a debugging change you meant to revert (lowered timeout, `dbg!`, a falsified constant from a negative control). If something is half-done at the end of a session, say so in the reply.

One logical change per commit; the message says what changed and why. End with the `Co-Authored-By:` trailer the harness specifies.

### Formatting

`just fmt` (`cargo +<pinned nightly> fmt --all`; `just fmt-check` checks) at `max_width = 120`. Use the pinned nightly: a different rustfmt formats differently. `.rustfmt.toml` lists the generated trees that must not be formatted (`hodow_cpu/src/cpu/auto_generated`, `hodow_cts/src/generated`, and the generated files elsewhere that carry a "Generated by" header). The generators that call `rustfmt` themselves pin `--config max_width=180` so their output, which `--check` compares, does not depend on that file - do not "fix" that. If you add a generated `.rs` file outside those trees, add it to the ignore list in `.rustfmt.toml`.

## Workspace layout

- `hodow_common` - what every module shares: the event protocol (`Event`, `Reporter`), the progress tree and live `RunState`, the results store with retention, the data directory. Depends on nothing else here.
- `hodow_cpu` - CPU test registry (`cpu/`, generated tests in `cpu/auto_generated`), features `cpu_suite`, `avx512`. Knows nothing of `hodow_bench`: the `--flows` tests join its registry through `set_extra_tests`. Module names inside the crate (`hodow_cpu::cpu::...`) are what the generated code refers to; do not flatten them.
- `hodow_gpu` - OpenGL tests (`opengl/`, feature `gpu`) and Vulkan compute (`vulkan/`, feature `vulkan`), shared burn types. Same `set_extra_tests` hook for the GL flows.
- `hodow_bench` - `bench/` and `flows.rs`; the GLES backend (feature `bench_gles`) pulls in `hodow_gpu`.
- `hodow` - the binary (`clap`), default features `["cpu_suite", "avx512", "gpu", "serve", "opencl", "bench_gles", "tflite"]`. Commands: `test` (`cpu`, `gpu`/`gl`, `vulkan`; bare `test` runs all), `burn`, `bench`, `cts`, `runs`, `serve` (also what bare `hodow` does), `info`, `dev coverage`. `cpu`, `gpu`, `vulkan` and `coverage` remain as hidden aliases: workers re-execute the binary through them and recipes and scripts call them (`Commands::normalized` maps both spellings onto one). `flows_glue.rs` registers the `--flows` tests into the CPU and GL registries; parent and isolated worker must both call it from `main`, or their test indices disagree.
- `hodow_cts` - Rust rewrite of the Khronos CTS (Vulkan, OpenGL ES, desktop OpenGL). A library plus its own binary, and a command of `hodow` (`hodow cts`, features `cts_opengles`, `cts_opengl`, `cts_vulkan`). Standalone: never `use` `hodow_cpu`, `hodow_gpu`, `hodow_bench` or `hodow_common`. See below and `hodow_cts/README.md`.
- `data/` - every hand-maintained input and captured output of the generators: `data/cpu/signatures.txt`, `detectable_features.txt` (both extracted from the pinned toolchain), `data/cpu/expected/<arch>/<ext>.txt` (captured on hardware), `data/cpu/function_policy.toml` (the one hand-maintained per-function list), `data/cpu/miri_only_functions.txt` (machine-generated), `data/gpu/*.csv`.
- No vendored stdarch: `extract_signatures.py` reads it from the pinned toolchain's `rust-src` (`--src` overrides). `winit/`/`glutin/` at the root are git-ignored local reference checkouts.

## Commands (via `just`; bare `just` lists them grouped)

- `run-*` groups (`run`: this machine, `run-cts`: the conformance cases, `run-serve`: the dashboard and its `submit*`, `run-board`: deploy to and run on another machine) answer a question about a machine; `dev-*` groups exist to work on hodow itself (`dev-variants`: release/ASAN shortcuts such as `gpur`, `ctsr`, `server`; `dev-board`: ssh access, debugging and fuzzing a board; `dev-cts`: diffs against upstream, coverage, fuzzing). A new recipe belongs in a `run-*` group only if someone testing a box would reach for it without thinking about arguments; its file in `just/` is named after its group.
- **Every `run-*` recipe leaves its output in `tmp/`** (usually via `scripts/run_logged.sh <slug> <cmd...>` -> `tmp/logs/<slug>/<ts>.log`, `tmp/<slug>-last.log`; it returns the command's own exit code). A new `run-*` recipe logs the same way. `hodow` also keeps its own log under `<data dir>/logs/` (`--log-file`, `--no-log-file`) and every run's results under `<data dir>/results/` (see "Runs, results and the dashboard"); the recipes export `HODOW_HOME=tmp/hodow` (the environment overrides it), so they never touch the real one.
- **Every `ssh`/`scp` to a board goes through `SSH_OPTS`** (justfile, and `$HODOW_SSH_OPTS` for `arm_fuzz_setup.sh`). Empty by default; only the environment changes it. Never make a key switch itself on.
- **Recipes running `hodow` in the default profile are pinned to the same `--features vulkan`** (`cpu`, `gpu`, `vulkan`, `stress`, `serve`, `server`, `submit*`; this is why `serve` shows a job's `current_exe()` as deleted after a rebuild - restart it). A different feature set rebuilds and unlinks the binary a running `serve` instance's `current_exe()` points at.
- Release binaries: `just binaries-linux <x86_64|aarch64|armv7|riscv64>` (zig, glibc 2.28), `binaries-windows` (mingw, zips with ANGLE's DLLs), `binaries-mac <aarch64|x86_64>`, each in a full, a CTS-only (not macOS) and a CPU-only variant (`variants=no` builds the full one only, which is all the workflows publish); `binaries` and `binaries-full` (with Vulkan the files keep the plain names, without it they are `*_no_vulkan*`; the SPIR-V is ~1.6 GB of `.rodata`, versus 40-80 MB for everything else, and it cannot link on armv7) are the x86_64 Linux plus Windows shortcut; the workflows publish both builds (a release asset may not exceed 2 GiB; the Linux Vulkan binary is 1.7 GB), the Vulkan one not for armv7. `.github/workflows/{linux,windows,mac}.yml` run them on every push to `master` and add the files to the release tagged `Nightly` with the secret `PAT_REPOSITORY`. Linux-only libc calls (`sched_*affinity`) must stay behind `cfg(target_os = "linux")`, or the macOS build breaks; check with `cargo +<NIGHTLY> check --target aarch64-apple-darwin -p hodow --no-default-features --features cpu_suite,serve`.
- **Any recipe building for arm/aarch64/riscv must be pinned to `NIGHTLY`** (dated nightly at the top of the justfile; bump that one variable) and `rustup target add ... --toolchain {{NIGHTLY}}` first. MSRV is `1.98`; no `rust-toolchain.toml` by design.
- Common: `just check`, `clippy`, `fmt`, `fmt-check`, `fix`, `info`, `cpu`/`gpu`/`vulkan` (`*r` = release, `*a` = ASAN), `stress`, `memtest`, `miri`, `doctor`/`setup`, `upgrade`, `gen-cpu-tests`, `gen-gl-table`, `coverage`, `serve-ui-test`, `cts*`, `cts-gles*`. The recipes live in `just/<group>.just` (imported by the root `justfile`, which keeps the variables).
- ARM boards: `arm`/`arm64`, `arm-cts`/`arm64-cts`, `install-arm*`, `arm-install <ip>`, `arm-cpu-run`, `arm-gpu-run`, `arm-cts-run` (GLES only; the board has no Vulkan), `test-board`, `arm-fuzz*`, `arm-probe`, `arm-reboot`, `arm-journal`, `arm-diag`, `findings-verify`. `cpu-remote <ip>` does the same for an x86_64 box (zigbuild pinned to its glibc; leaves `tmp/cpu-remote-last.{log,json}`).
- **Read the `--report` JSON, not the log, to capture expected values** from an `--isolate` run (`scripts/cpu/capture_expected.py --from-report ...`); an unverified test's observed value exists nowhere else.
- `just burn`, `bench`, `arm-burn`, `arm-bench` write their own record under `tmp/burn*`/`tmp/bench*` (no pipe, to keep bars and colours). Bench builds use `--no-default-features` into `target/bench`. **Any `--no-default-features` build that should test CPUs must name `cpu_suite`**, or the registry is an empty stub.
- Feature flags of `hodow`: `cpu_suite`, `avx512`, `gpu`, `vulkan`, `opencl`, `tflite`, `bench_gles`, `serve`, `miri_build`, and `cts_opengles`/`cts_opengl`/`cts_vulkan` (off by default). `hodow` builds without `gpu` too (the CPU-only and CTS-only variants rely on it). **Memory: never `cargo check --workspace --all-targets` (OOMs a 29 GB box).** Check one package, with `CARGO_BUILD_JOBS=4 CARGO_PROFILE_DEV_DEBUG=0` or `hodow_cts/scripts/guarded_cargo.sh` (peaks: `hodow` 13 GB, `hodow_cts` 10 GB, `hodow_cts --features vulkan` 20 GB; see `docs/building.md`).
- `just info` prints through `println!`, not `log` (it is a report). `OpenGLMode::create_with_opts` ignores `display_api`/`gl_api` when `$DISPLAY` is unset, so varying them proves nothing about a headless box.

## CPU test generation - do not hand-edit generated files

`hodow_cpu/src/cpu/auto_generated/` is entirely generated by `scripts/cpu/generate_tests.py` from `data/cpu/signatures.txt`. **Never hand-edit it and never run `cargo fmt` on it** - regeneration must stay idempotent and diff-clean. Change the generator or `function_policy.toml` and re-run. Files split as `<arch>/<ext>/<operation>.rs` by `module_for`, based only on the function's own name (never positional chunking).

- **What the extractor cannot see is not tested, and nothing says so** (const-stabilization once silently dropped 3324 intrinsics). Re-check `hodow coverage` (the *discovered* count) after any toolchain/upstream bump, not just failures.
- **No captured expected value => `Verdict::Unverified`, never a pass.** `Checked` = compared against a hardware-captured value; `Unverified(Some(v))` = observed value, capturable; `Unverified(None)` = nothing to compare, ever; `Skipped(reason)` = body returned before executing. Always read the Unverified count next to the pass count. Unverified does not fail the exit code. An absent entry is not a captured zero.
- **Everything a test produces is compared**: store destinations are read back (64-byte window, `black_box` between call and read is load-bearing), integer returns at real width, scalar float returns, tuples for value-plus-out-param functions. Unchecked calls still go through `black_box` so the instruction really executes. Outputs that are not a function of the arguments use `skip_output_check`/`skip_result_check`.
- **Property tests** (`property_tests`, x86 only) compare an intrinsic against a different one on the same chip (masked vs unmasked, narrow vs wide, commutativity...), needing no captured value. They exclude scalar `_ss/_sd/_sh`, width-changing ops, and require matching const generics; a captured value for one is deleted by `drop_shape_mismatched_expected`.
- **The binary is portable**: no `-C target-cpu=native`, no crate-wide `target-feature`. Every test is a `#[target_feature]` `_impl` plus a safe wrapper; every extension is compiled in and gated only by the runtime detect fn. `cmpxchg16b` (via `.cargo/config.toml`) is the one crate-wide exception; `rtm` is in `SKIP_EXTENSIONS`. Note `RUSTFLAGS` in the environment *replaces* config rustflags.
- **Compound `#[target_feature]` functions** get a generated runtime guard for every feature beyond the group's own (`extra_feature_guard_lines`, checked against `detectable_features.txt`). **Key Locker is gated on `common::x86::keylocker_usable()`**, not `is_x86_feature_detected!` (CPUID presence bit != enabled by the OS; the macro also short-circuits on `cfg!(target_feature)`). Any feature whose CPUID bit means "present" rather than "enabled" needs the same.
- Test names: `test_<arch>_<ext>_<intrinsic-without-leading-underscore>`. `miri_tester.py` and `miri_tester_sorter.py` reconstruct intrinsic names from them - update both if the scheme changes.
- **`function_policy.toml`** is the only hand-maintained per-function input; only what stdarch cannot say belongs there (a hardware fault, an architecturally undefined result). `reason` is mandatory, unknown keys are errors, stale entries warn. Keys: `params.<n>`+`no_fuzz`, `skip_result_check`, `skip_output_check`, `check_lanes`, `no_value_scenarios`, `consts.<NAME>`, exclusions. Re-enabling an excluded function: remove entry, regenerate, capture on hardware, regenerate, run; if it segfaults it goes back.
- **Const-generic ranges are read from stdarch's own asserts** (`!NAME=lo-hi` in `signatures.txt`, `~r` rounding, `~l` lane index clamped to the lane count), never guessed from a name. Two places a derived range is not final: lane indices and NEON scalar `_n_` immediates (`scalar_immediate_bound`, an out-of-range one is an LLVM "Cannot select" that kills the whole aarch64 build).
- **Scenario expansion** (`in_pilot_scope`): value axis (`normal2/3`, `boundary_*`, `asym_*`) for x86/x86_64 and NEON; immediate axis (`_imm_<v>`, `IMMEDIATE_AXIS_ARCHS`) derived from the asserted range. SVE is excluded from the value axis (scalable vectors, broadcast-and-extract model; VL-dependent functions excluded by `SVE_VL_DEPENDENT_RE`). `gather`/`scatter` are permanently excluded (an extreme index is an out-of-bounds read). When widening scope breaks a compile, delete the stale entries from `data/cpu/expected/` and recapture rather than editing generated code.
- **NEON groups are split by the feature each function really needs** (`rebucket_neon_by_feature`); on arm32 anything without an `is_arm_feature_detected!` string is "no detection" and skipped. `arm_shared` is one expected-value file for two architectures that disagree on denormals (use the smallest normal there, `_MIXED_FLOAT_CYCLE_DUAL_ARCH`). Capture aarch64 first, armv7 second, then verify **both**.
- **Cross-capture** needs no distro gcc: `capture_expected_cross.py <target> zig <qemu>` (musl targets, `zig_cross_linker.sh`, static binary under qemu-user). qemu lacks FAMINMAX/LRCPC3/LUT - pass a `-s` skip list when capturing through it. A qemu value is emulation, not silicon.
- `arm_shared` is compiled for both targets; hard `#[cfg(target_arch)]` gates upstream are carried onto wrapper and registry entry (`arch_only_cfg_line`). `float64x*_t` helpers are aarch64-only.
- Miri: warm the cache with `just cpu -f` before `miri_tester.py`; pass `--threads N` on small machines (24 default OOMs a 29 GB host); it buffers its output until exit. `keylocker_usable` needs its own `cfg!(miri)` guard.
- Sensitive-to-build-profile functions (`_mm_extracti_si64` family): only the lower 64 bits are defined, so `check_lanes = 2`.
- **Isolate runs** (`test cpu --isolate`, `test gpu --isolate`) attribute results by index; parent and worker must compute the same filtered list (`should_skip_test_or_feature`), and `FlowArgs` are forwarded to children. Run a full `--isolate` pass on new hardware *before* a non-isolated capture, since a crash mid-capture loses everything after it.

## GPU (OpenGL) testing

- Each test implements `GLTest` (`hodow_gpu/src/opengl/test_trait.rs`) in its own file under `opengl/tests/`, registered in `tests/mod.rs`. `es3_validation.rs` is the GLES-native half (`#version 300 es`/`310 es`, no `glGetTexImage`/`glGetBufferSubData`, bind a VAO, colours as `n/255.0`). Many other tests target a core profile: bind a non-zero VAO, look up uniform locations.
- `context.rs` creates a headless context; order with no `$DISPLAY`: Wayland compositor's `wl_display`, EGL device platform, default display. A Wayland-only driver (i.MX/Vivante) refuses the last two. `WAYLAND_DISPLAY`/`XDG_RUNTIME_DIR` are defaulted from `/run/user/<uid>` sockets that actually exist (`default_wayland_env`; copied into `hodow_cts` since it cannot depend on core). `just gpu` with a window needs a display; use `--no-window` headless.
- Call `drain_gl_errors()` before a test; the harness fails a test that leaves a pending GL error. `run_one_test` classifies passed / **not supported** / failed. A test whose `gl::Foo(` calls are not loaded is skipped before it runs (`generated_requirements.rs`, from `generate_gl_table.py`); the panic catch is a backstop. Never print "all passed" without the not-supported count. `[GL debug]` messages are capped per test (`MAX_DEBUG_MESSAGES_PER_TEST`).
- `opengl/FUNCTIONS_TABLE.md` is generated (`just gen-gl-table`) - rerun after touching `opengl/tests/`, don't hand-edit.
- Vulkan compute (`vulkan/mod.rs`): `ash` + `naga` (WGSL -> SPIR-V at run time). Missing loader/ICD is a clean skip (exit 0), distinct from an `init_error`.

## Flows, burn, bench

- **Flows** (`hodow_bench/src/flows.rs`): whole pipelines as tests, using the same implementations `bench` times (`bench::execute`). **Opt-in: nothing runs without `--flows`** (`--flows-size full` for 1080p-class). Integer only, bit-exact; every frame checked; tiled flows stitch results against the whole-frame reference.
- **Burn** (`hodow/src/burn/`): the orchestrator runs no test; each sub-test is a `burn --worker <json>` process judged only by its `@burn {json}` lines and how it ended (`[CRASH]`, `[HANG]` after `--hang-timeout`, bounded reap). Every expected value is computed, never captured. Memory reads go through `black_box`. **`--selftest` (`just burn-selftest`, release) is the gate**: each detector gets a fault injected and must report it. Its own `events.jsonl` (in `burn/` inside the run's folder, so it does not collide with the session's) is `sync_data`'d per line so it survives a power cut. In the combined phase RAM and GPU memory are one budget split by the orchestrator (a shared-memory SoC counts CMA twice otherwise).
- `--stress` and `--memtest` stay flags of `test cpu`/`test gpu` rather than `burn` phases: `burn` needs Unix process groups and signals, and Windows is a target.
- **Bench** (`hodow_bench/src/bench/`, `hodow/src/bench/`): a frame is timed as upload + compute + download from/to ordinary CPU memory; every row is checked against one CPU scalar reference (integer variants bit-exact, f32/f16 tolerance 1). Rows run in long-lived workers per backend family. GLES and Vulkan share one set of WGSL kernels (`shaders.rs`); **`shaders::without_for_steps` is required because the Vivante GLSL compiler drops the first iteration of naga's `for` loops** - never use `continue` in a kernel.

## Runs, results and the dashboard

- **One protocol for every module** (`hodow_common::Event`): `RunStarted`, `StepStarted/Progress/Finished` (a tree: `done/total`, unit, weight), `Finding` (one per test, with a `Verdict`), `Log`, `RunFinished`. A module takes a `Session` (`hodow/src/session.rs`), emits through its `Reporter` and calls `session.finish(..)` **before** any `process::exit` (a `Drop` does not run then). `--events` prints the lines as `@hodow {json}` on stdout; anything else on stdout is ignored by readers.
- **Progress is honest**: a step with no known total is indeterminate (`fraction` is `None`), a fraction never reaches 1.0 before the step finishes, a parent shows a percentage only when every child declared a weight, ETA only after a few samples. Progress events are throttled and never written to a result file.
- **Results store** (`hodow_common::store`): `<data dir>/results/<time>-<module>/` with `meta.json` and `events.jsonl` (gzip when the run ends; flushed once a second, anything not a pass at once with `sync_data`; a torn last line is skipped on read). Retention trims the whole data dir to 5 GiB oldest first, never a running or pinned run or the newest of each module. A run silent for an hour reads as interrupted. Run ids come from the network, so they go through `is_valid_id`.
- **`hodow serve`** (`hodow/src/serve/`): a job is a `hodow ...` command line, run as a child with `--events`; the server builds a live `RunState` from its stdout and the child saves its own results. `jobs::validate` parses the arguments with the real clap definition and refuses what could write outside the results folder (`--out`, `--report`, `--background`, `--log-file`, `--data-dir`, worker flags) - the server has **no authentication by design** and listens on `0.0.0.0:7878` (`--local` restricts it). GPU availability is asked of `hodow probe` in its own process with a timeout, never in the server. A cancelled job's process group gets SIGTERM, then SIGKILL, and its run is marked cancelled (`Store::finish_abandoned`).
- **The page** (`hodow/src/serve/ui/`) is plain HTML/CSS/JS embedded with `include_str!`: no CDN, no build step, nothing fetched at run time. Rendering is pure functions (state to HTML) so `just serve-ui-test` (`node --test`, Node 22) checks it without a browser, including that everything a test can print is escaped. It has not been looked at in a real browser from this container.
- `burn` still has its own dashboard (`--no-http`/`--http-port`): the sensor charts and kernel log have no counterpart in the event stream yet.

## hodow_cts (Khronos CTS port: Vulkan, OpenGL ES, desktop OpenGL)

Pinned to upstream `31807adf6` (`hodow_cts/upstream/COMMIT`); a hand-picked, growing subset. Detail in `hodow_cts/README.md`.

- **Ported code keeps the upstream C++ shape** (same `checkSupport`/`initPrograms`/`iterate` split, order, names). Idiomatic Rust only where it removes a real hazard. Re-syncing with upstream depends on it.
- `QUIRKS.md` is for external findings only (upstream C++ bugs preserved verbatim, confirmed driver behaviour). Nothing about this port's own code or scripts.
- **`shaders/manifest/*.toml` is the only place a test parameter is written down**; `compile_shaders.py` substitutes it into the GLSL and emits the Rust constant. Never hand-edit `src/generated/`. SPIR-V is committed as `.spv` blobs `include_bytes!`'d - **never turn it back into `[u32; N]` literals** (30+ GB of rustc memory), never collapse the split-per-manifest files or raise `PART_SIZE_LIMIT` (GitHub size limits). GLSL sources are packed beside the SPIR-V (`.glsl`, `include_str!`'d via `glsl_text`). `--check` also fails on stale files.
- glslang and `deqp-vk` are developer tools, never build/runtime dependencies; the binary links only libc/libgcc.
- Add every ported upstream file to `hodow_cts/upstream/FILES.txt`, or it silently stops being tracked.
- **A ported group is not done until `just cts-diff` (Vulkan) / `cts-gles-diff` (GLES) agrees with upstream.** It only catches verdict-changing divergences. Periodically diff a *whole* root, not just the group just ported (that is what caught the ES 3.1/3.2 context bug). `--validation` is a second axis, not a conformance run.
- **A clean run proves nothing about skipped cases**: always report the `Not supported` count next to passes. SwiftShader lacks tessellation/geometry/push descriptors/maintenance6 and passes cases a conformant driver rejects; prefer lavapipe (`cts-sw`/`cts-swr`), and use `just cts-val` (validation layer) for anything that crashes or hangs only on real hardware. Only a validation ERROR fails a case.
- **"No driver" is never a failure**: exit 2.
- **Desktop OpenGL.** `KHR-GL30`...`KHR-GL46` (feature `gl`, `just cts-gl-diff`) are ports of the Khronos GL CTS, one root per version, each on a core context of exactly that version, gated against the real `glcts` (`just glcts-build`; `diff_vs_deqp.py --glcts`) like the ES roots: a group is not done until it agrees.
- **The compiled-in half is a Cargo feature; default is `gles` alone** (Vulkan adds 67 MB SPIR-V and 625k registrations). The axis is API, never age: three features, `gles`, `gl` (implies `gles`) and `vulkan`, and on the `hodow` binary `cts_opengles`, `cts_opengl`, `cts_vulkan`. Vulkan recipes must ask for it (`HODOW_CTS_FEATURES=vulkan`, `--features vulkan` for `cts-diff`); `cts-verify` builds, clippies and tests every combination. A half that is not compiled in says so (`note_compiled_out_halves`). Frameworks (`tcu`, `vk`, `glu`, `glw`, `eglw`, `runner`) stay unconditional - `main.rs`, `cli.rs`, `runner/`, `fuzz/` contain no `cfg`.
- **The command line is a library function** (`hodow_cts::cli::main_from`); `main.rs` only calls it, so the same code runs as `hodow_cts` (what the ARM board recipes copy) and as `hodow cts`. A run reports through `cli::Observer` (plan, every result, exit code) - `hodow` turns that into a saved run. The runner re-executes itself for workers and the fuzzer's probe through `isolate::reexec_command`, which inserts the prefix `hodow` sets (`cts`); a new place that spawns the binary again must use it.
- Case trees are built only for roots a run could select (literal head of each pattern before its first `*`).
- **Run the binary with `ulimit -c 0`** (`run_cts.sh` does it); a crashing worker drops cores of up to ~1 GB. `rm -f core.*` after a crash. `compile_shaders.py --keep-going`, `guarded_cargo.sh` exist for building under memory limits.
- **The Vulkan half is five crates so no rustc process needs more than ~8 GB** (one crate took ~19 GB): `hodow_cts/crates/{base,vk_main,vk_a..vk_d}`. `base` (`src/base.rs`) is everything but the Vulkan test groups and `cli`; `vk_*` are the groups listed in `vk_crates.toml`, each crate's roots generated by `scripts/vk_crates.py` (`--check` is in `cts-verify`) and its shaders by `compile_shaders.py` into `src/generated/vk_<crate>/`. All files stay where they were and are loaded with `#[path]`; groups keep saying `crate::tcu`/`crate::vkt::...` because each crate root re-exports the base. Anything a group in one crate uses from a group in another must be `pub`, not `pub(crate)`. Cases reach `base` through `set_case_providers` (`install_case_providers` in `cli::main_from`). A new group goes into `vk_crates.toml`; measured peaks: main 3.4 GB, a 5.4, b 1.1, c 8.1, d 4.1.
- **The two APIs share the framework and nothing else**: `tcu`, `report`, `runner` are API-agnostic (generic over `vkt::TestCase`/`glu::TestCase`); a third API is a module plus an `Api` variant. Don't push API knowledge down into them.
- **GLES half**: `glw.rs`/`eglw.rs` are generated from upstream `.inl` by `gen_api_wrappers.py` (`just cts-wrappers`, `--check` in `cts-verify`); calling an entry point the driver lacks panics with its name (a port bug). **No shaders are committed for GLES** (the driver's compiler is under test; `format!` where C++ uses `<<`); `HODOW_CTS_DUMP_SHADERS=1` prints every source. Display lookup is `src/eglu/mod.rs` (device, surfaceless, Wayland, default). Offsets/strides come from `glu::get_program_interface_*`, never assumed std430. The render target must be requested as d24s8 (`eglu::choose_config`; diff runs use `--deqp-gl-config-name=rgba8888d24s8ms0`). Each root runs on the context version upstream asks for (ES 3.1 root: 3.2 then 3.1). `glu::reset_state_es` runs after every GL case. Negative-API groups are the cheapest cases to add. The ES roots are ES only, deliberately.
- `Outcome::Crashed` carries why the child died (`isolate::crash_reason`): SIGILL = instruction unavailable, SIGKILL is usually the OOM killer.
- Report `just cts-coverage` after every batch of newly ported tests; `is_stub` marks cases registered without an instance.
- **Fuzzing** (`just cts-fuzz <verb>`, `hodow_cts fuzz`) fuzzes *which cases share a process and in what order*. Rules easy to break: the in-flight record is fsynced before the group runs and what it means is a person's call (`continue`, `--last-was-fine`); verdicts must stream to the supervisor while a group runs; a timed-out worker in `D` state is reported after `REAP_GRACE`, never waited on; quarantine excludes the *trigger* (first of the minimised list), not the casualty, is per-machine, needs a `reason`, and is not committed; `arm-fuzz` never deploys (it would change the corpus fingerprint); `findings/` is git-ignored. **`just cts-fuzz-selftest` is the gate** (a clean campaign proves nothing).
- **`just test-board <ip>`** drives a board unattended over ssh (`hodow_cts/src/board/`, results keyed by SoC serial and driver version). A "does not reproduce" is never believed after one run; do not speed this up by trusting a single run. `src/board/sim.rs` (`cargo test board::`) is the gate. Reboot method matters (`arm-reboot`: sysrq is the default; there is deliberately no watchdog method - on i.MX6 it reboot-loops the board). `just arm-probe <ip> '<glob>'` before bisection; `just arm-diag <ip>` before rebooting a wedged board, since nothing it shows survives one.
- The dev container ships lavapipe and `VK_LAYER_KHRONOS_validation`. Add packages by editing `~/.claude/skills/NOT_SKILL/Dockerfile` and asking for a rebuild.
